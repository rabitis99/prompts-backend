# Prompt 서비스 MVP+ 출시 전략

> 설계 고도화 단계를 종료하고 실사용자 데이터 확보 단계로 전환하는 제품 전략 문서.
> 기술적 완성도보다 **사용자 행동 신호**를 최우선 판단 기준으로 삼는다.

---

## 1. 출시 전 보류 기능

> 지금 구현하면 사용자 신호 없이 복잡도만 늘어나는 기능들이다.

| 기능 | 보류 이유 | 재개 조건 |
|------|---------|---------|
| **Self-Consistency 실험** | +2~4 LLM 호출 비용 발생. 정확도 상승률이 실제 사용자에게 의미 있는지 검증 전 | DAU 100+, 30일 Objective별 호출 분포 확인 후 |
| **Tree-of-Thoughts 실험** | PLANNING 사용 패턴 자체가 불명확한 상태에서 ToT 실험은 무의미 | PLANNING Objective 실사용 비율이 전체의 15%+ 달성 시 |
| **3축 승격 수식 고도화** | α·β 가중치 초기값(0.4/0.6)은 추정치다. 실제 트래픽 없이 튜닝하면 잘못된 정밀도를 가진 수식이 된다 | 30일 A/B 실험 데이터 축적 후 |
| **Dynamic Golden Set 자동화** | 자동화 인프라를 먼저 만들면 유지 비용이 생긴다. 트래픽이 없으면 의미 있는 샘플도 없다 | 일 요청 수 200+ 안정화 이후 |
| **전략 번들 확장** | 현재 3계층으로 충분하다. 추가 번들은 사용자 편집 패턴이 특정 품질 한계를 드러낼 때 대응하는 것이다 | 편집률이 특정 Objective에서 지속적으로 40%+ 발생 시 |
| **고급 A/B 실험 인프라** | 실험 설계·통계적 유의성 확보·그룹 분리 로직은 수개월 작업이다. 기준 트래픽 없이는 의미 없다 | 안정적 DAU 기준선 확보 + LLM 비용 예산 확정 후 |

## 2. 출시용 최소 기능 정의 (MVP+)

### 반드시 포함

| 기능 | 이유 |
|------|------|
| **Core 전략 고정** (CLARIFY_FIRST, STEP_BY_STEP, CHECKLIST_VERIFY) | 추가 LLM 호출 없이 기본 품질 보장. 제거 불가 |
| **Objective 자동 매핑** | 이것이 제품의 핵심 가치다. 사용자가 Objective를 직접 선택하게 만드는 순간 이 제품은 "도구"가 된다 |
| **Verify-Repair 1회** (2회 → 1회로 축소) | MVP 단계에서 지연 리스크 최소화. 품질 충분성은 편집률로 검증 |
| **Result Badge UX 3종** (✅ 조건 반영됨 / ✅ 형식 검증 완료 / ✅ 금지어 없음) | 내부 품질을 사용자 신뢰로 변환하는 최소 인터페이스. UX의 핵심 |
| **PromptVersion 저장** | 재사용·이력 추적의 기반 데이터. 없으면 Phase 2에서 아무것도 측정 못한다 |
| **최근 실행 이력 조회** | 재방문 사용자가 돌아왔을 때 가장 먼저 보는 화면. 재방문 신호 측정 전제 |

### 반드시 제거/보류

| 제거 항목 | 이유 |
|---------|------|
| Verify-Repair 2회 | MVP 단계에서 지연 리스크가 품질 이득보다 크다. 편집률 데이터로 실제 필요성 확인 후 복구 |
| 즐겨찾기 | 재방문 패턴이 존재하는지 먼저 확인해야 의미가 있다. Phase 2로 이동 |
| 성공률 기반 추천 | 추천 알고리즘은 이력 데이터가 쌓여야 의미 있다. 데이터 없는 추천은 노이즈다 |
| ⚡ 빠른 생성 / 🔄 재검증 완료 배지 | MVP에서 과도한 정보. 3종 기본 배지만으로 신뢰 충분 |
| QualityPriority enum 노출 | 자동 매핑 원칙 위반. 사용자 입력 UI에 노출하지 않는다 |
| Dynamic Golden Set | Phase 3 이후 |

### 절대 빼면 안 되는 UX 요소

1. **자동 매핑 — 사용자는 아무것도 설정하지 않아도 결과가 나온다**
   입력 → 결과의 경로에 선택 단계가 생기면 전환율이 즉시 떨어진다.

2. **Result Badge — 사용자는 "왜 이 결과를 믿어야 하는가"에 답이 필요하다**
   수치를 보여주지 않아도, 배지 3개가 있으면 "검증됐다"는 신뢰를 만든다.

3. **이력 조회 — 사용자가 돌아올 이유를 만든다**
   재방문 이유가 없으면 7일 재방문율이 5% 이하로 떨어진다.

## 3. 실사용자 검증 핵심 지표

> pass rate는 내부 엔진 지표다. 제품 지표가 아니다.
> 다음 지표만으로 제품이 작동하고 있는지 판단한다.

### 1순위 지표 — 복사했는가

> **복사하면 쓴다. 복사 안 하면 장난감이다.**
> 이 하나의 행동이 다른 모든 지표보다 직접적이다.

| 지표 | 의미 | MVP 목표 | 위험 신호 |
|------|------|---------|---------|
| **생성→첫 복사까지 걸린 시간** | 결과 노출 후 복사 버튼을 누르기까지의 시간. 짧을수록 결과가 즉시 쓸 수 있는 상태 | 중앙값 < 10초 | 중앙값 > 60초 또는 복사율 < 40% → 결과가 그대로 쓸 수 없는 상태 |

**왜 이 지표인가:**
- 저장·북마크·재방문은 모두 "나중에"의 행동이다. 복사는 "지금 당장" 쓰겠다는 신호다.
- 복사 없이 세션이 끝나면, 사용자는 결과를 읽고 버린 것이다.
- 복사까지 10초 vs 60초의 차이는 "읽어보니 쓸 만함"과 "상당 부분 고쳐야 함"의 차이다.

**구현:** 결과 화면에 명시적 "복사" 버튼을 두고 클릭 이벤트를 로깅한다. 클립보드 API 직접 감지는 브라우저 정책 이슈가 있으므로 버튼 경유가 필수다.

---

### 2순위 지표 — 계속 쓰는가

| 지표 | 의미 | MVP 목표 | 위험 신호 |
|------|------|---------|---------|
| **생성 후 수정률** | 복사 후 즉시 편집 비율. 복사 없이 편집만 하면 결과가 기대에 못 미친 것 | < 40% | > 60% → 엔진 품질 문제 |
| **동일 프롬프트 재사용률** | 한 번 생성한 결과를 이력에서 다시 꺼내 쓰는 비율 | > 20% | < 10% → 보관 가치 없음 |
| **북마크 비율** | 세션당 북마크 발생 비율. 고가치 출력의 신호 | > 10% | < 5% → 출력 차별화 부족 |
| **7일 재방문율** | 첫 방문 후 7일 내 재방문 비율. 서비스 습관화 여부 | > 25% | < 15% → 지속 사용 이유 없음 |

### 지표별 해석 규칙

- **복사율 < 40%** → 결과 자체가 문제. 엔진(Verify 강도, Objective 매핑 정확도) 점검.
- **복사율 정상 + 수정률 높음** → 결과는 방향이 맞지만 완성도가 낮음. Repair 횟수 복구 검토.
- **복사율 정상 + 재방문 낮음** → 결과는 쓸 수 있지만 다시 올 이유가 없음. 이력·추천 UI 개선.
- **복사 시간 > 60초** → 결과를 훑어보는 데 시간이 걸림. 길이·구조 문제일 가능성. 수정률과 교차 확인.

## 4. 3개월 실행 전략

### Phase 1 (0~4주): 출시 준비 + 첫 사용자 확보

**목표:** 작동하는 제품을 실제 사용자 손에 전달한다.

| 항목 | 내용 |
|------|------|
| **구현** | MVP+ 6개 기능만 구현. Core 전략 + Objective 자동 매핑 + Verify 1회 + Badge 3종 + Version 저장 + 이력 조회 |
| **측정** | **생성→첫 복사 시간 (최우선)**, 복사율, Badge 배포 분포, 편집률 |
| **고치지 말 것** | 전략 로직, Verify 기준, 도메인 모델 — 첫 3주는 코드보다 사용자 반응 관찰 |
| **전환 신호** | **복사율 < 40% 지속** → 엔진 품질 점검 우선. 편집률 > 60% → Verify 2회 복구. 일 생성 수 < 5건 지속 → 유입 채널 문제, 기능 개선 아님 |

**Phase 1 원칙:** 기능을 추가하지 않는다. 문제를 발견해도 2주는 관찰만 한다.

---

### Phase 2 (4~8주): 로그 기반 개선

**목표:** 사용자 행동 데이터로 무엇을 고칠지 결정한다.

| 항목 | 내용 |
|------|------|
| **측정** | 7일 재방문율, 재사용률, 북마크 비율 추가 측정. Objective별 편집률 분포 분석 |
| **개선 후보** | 편집률이 높은 Objective 식별 → 해당 Objective만 Verify 2회로 선별 복구 |
| **추가 기능** | 즐겨찾기 (재방문 패턴 확인 후), 편집률이 높은 결과 유형에 맞는 Badge 추가 |
| **고치지 말 것** | Experimental 전략. Static Golden Set이 확보되기 전 A/B 실험 시작 금지 |
| **전환 신호** | 재방문율 > 25% + 재사용률 > 20% → Phase 3 진입 가능. 재방문율 < 15% 지속 → UX 재검토 (기능 추가 아님) |

---

### Phase 3 (8~12주): 전략 실험 재개 여부 판단

**목표:** 엔진 고도화 재개 여부를 데이터로 결정한다.

| 재개 조건 | 판단 기준 |
|---------|---------|
| A/B 실험 재개 | DAU 100+, 30일 트래픽, 편집률 < 35% (기준선 안정) |
| Dynamic Golden Set | 일 요청 200+, 이력 저장 90일 누적 |
| Self-Consistency 실험 | FACTUAL Objective 편집률이 타 Objective 대비 지속적으로 15%+ 높을 때 |
| 승격 수식 α·β 튜닝 | 실험군/대조군 30일 데이터 확보 후 |

**판단 원칙:**
- 편집률이 40% 아래로 안정되고 재방문율이 25% 이상이면 → 엔진이 충분하다. Phase 3에서도 UX 개선 우선.
- 편집률이 40% 이상으로 정체되면 → 엔진 고도화 재개. Verify 2회 + Experimental 단계적 투입.

## 5. 제품 전략적 경고

### 지금 가장 위험한 과설계 요소

> **3축 승격 수식 (정확도 / (호출가중치 + 지연가중치))**

이 수식의 α·β 초기값(0.4/0.6)은 실증 데이터 없이 설정한 값이다.
지금 이 수식을 운영에 반영하면, 잘못된 정밀도를 가진 의사결정 도구가 된다.
수식은 문서에 정의된 채로 보류하고, Phase 3에서 실제 A/B 데이터로 초기값을 교정해야 한다.

---

### 엔진 중심 사고에서 벗어나기 위한 운영 원칙

```
사용자가 결과를 편집하지 않으면 엔진이 잘 작동하는 것이다.
사용자가 돌아오면 제품이 작동하는 것이다.
둘 다 측정하기 전에는 아무것도 개선하지 않는다.
```

| 엔진 중심 사고 (피해야 할 것) | 제품 중심 사고 (지향해야 할 것) |
|--------------------------|--------------------------|
| pass rate를 높이면 좋은 제품이다 | 편집률이 낮으면 좋은 제품이다 |
| 전략이 많을수록 정확도가 높다 | 사용자가 원하는 결과를 빨리 주는 것이 정확도다 |
| A/B 실험이 품질을 보장한다 | 재방문율이 품질을 보장한다 |
| 설계가 완성되면 출시한다 | 출시 후 데이터가 설계를 완성한다 |

---

### 엔진 고도화 모드로 돌아갈 시점

다음 **두 조건을 동시에** 충족할 때만 엔진 고도화로 복귀한다:

1. **행동 신호:** 편집률이 35% 아래로 안정되지 않고 **특정 Objective에서 지속적으로 높다**
   → 이 경우에만 해당 Objective의 전략·Verify를 강화한다.

2. **규모 신호:** DAU 100+, 30일 안정적 트래픽
   → 이 규모 이전의 엔진 개선은 수요 없는 최적화다.

**이 두 조건 중 하나라도 충족되지 않으면 엔진은 현재 상태로 동결하고 UX 개선에 집중한다.**
